# PRP: Agent Variants — multiple "Claude" entries in the dropdown via CLI parameters

**Date:** 2026-09-01
**Feature:** Let the 🫴 dropdown show several launch options for one CLI agent (e.g. `Claude Fable`, `Claude Sonnet`, `Claude Opus (skip permissions)`), each running the same binary with extra command-line parameters. Built-in presets for Claude Code + user-defined custom variants for any agent.
**Confidence Score:** 9/10
**Semver:** MINOR → `0.6.0` (see "Versioning decision" below)

---

## Goal

After this PRP, a user who has Claude Code enabled sees, directly under `🫴 Claude Code` in the dropdown:

```
🫴 Amp CLI
🫴 Claude Code
🫴 Claude Fable
🫴 Claude Opus
🫴 Claude Sonnet
🫴 Codex CLI
...
```

Clicking `🫴 Claude Fable` opens a terminal tab titled `🫴 Claude Fable` running `claude --model fable`.
In **Settings > Tools > LLM Brains** the user can toggle each preset (indented checkbox under its parent agent) and add custom variants for any agent in a text area, one per line: `Label | extra args` (Claude) or `agent-id | Label | extra args` (any agent).

## Why

- Users switch models/permission modes per task; today that means typing flags by hand in the terminal every time.
- Model aliases (`fable`, `opus`, `sonnet`) change meaning over time; presets in the plugin track them, custom rows cover anything else (`--effort max`, `--permission-mode plan`, `--model claude-opus-4-6`).
- The mechanism is generic (variant = parent agent + label + extra args) so Codex/Gemini/… can get presets later with zero new plumbing.

## What

### User-visible behaviour
1. Dropdown: for every **active** built-in agent, its active variants are listed **flat, immediately after** the agent's own entry, same 🫴 prefix. No submenu.
2. Variants are shown only when the parent agent is active (auto-detect keeps driving parent agents; variants inherit).
3. Settings panel:
   - Under `Claude Code` row: indented checkboxes for the four presets, showing label + the effective command.
   - New "Custom variants" section: a multi-line text area. One variant per line. Blank lines and lines starting with `#` are ignored.
   - Preset toggles and text area persist in `LlmBrainsAgentSettings.xml` like every other setting.
4. Terminal tab title = `🫴 <variant label>`; command = `<agent.command> <extraArgs>` (trimmed), executed verbatim by the IDE shell (bash/zsh/PowerShell) — no escaping layer, exactly like the custom agent command today.
5. Check-all / update-all / detect-all are **unchanged**: they operate on binaries (`CodingAgents.all`), and variants share their parent's binary.

### Built-in presets (all for `agentId = "claude"`)

| id | label | extraArgs | default |
|---|---|---|---|
| `claude-fable` | Claude Fable | `--model fable` | on |
| `claude-opus` | Claude Opus | `--model opus` | on |
| `claude-sonnet` | Claude Sonnet | `--model sonnet` | on |
| `claude-opus-skip-permissions` | Claude Opus (skip permissions) | `--model opus --dangerously-skip-permissions` | **off** |

Use the CLI aliases, not pinned names: `claude --help` says `--model` accepts "an alias for the latest model (e.g. 'fable', 'opus', or 'sonnet') or a model's full name (e.g. 'claude-fable-5')". The user's example "Opus 4.6" is achievable with a custom line `Opus 4.6 | --model claude-opus-4-6`. The skip-permissions preset is off by default on purpose — it must be an explicit opt-in.

## Implementation Blueprint

### Data model

```kotlin
// CodingAgents.kt — add below CodingAgent
data class AgentVariant(
    val id: String,              // stable for presets ("claude-fable"), synthetic for custom lines
    val agentId: String,         // parent CodingAgent.id
    val label: String,           // "Claude Fable" — shown in dropdown + terminal tab
    val extraArgs: String,       // "--model fable"
    val defaultEnabled: Boolean = true,
) {
    val dropdownLabel: String get() = "$HAND_EMOJI $label"

    fun commandFor(agent: CodingAgent): String = "${agent.command} $extraArgs".trim()
}
```

Settings state additions (all with defaults → backwards compatible):

```kotlin
var activeVariantIds: MutableList<String> = mutableListOf(),   // presets explicitly turned ON  (needed for defaultEnabled=false ones)
var inactiveVariantIds: MutableList<String> = mutableListOf(), // presets explicitly turned OFF
var customVariantLines: String = "",                            // raw text-area content, parsed on read
```

Why two lists instead of one: presets have per-item defaults (skip-permissions is off by default). Storing explicit ON and OFF overrides keeps semantics stable even if a preset's default flips in a later release. Only store an override when it differs from `defaultEnabled`.

Custom line grammar (parser, `CustomVariantParser.parse(text)`):
```
# comment                                  → ignored
                                           → blank, ignored
Label | extra args                         → agentId = "claude"
agent-id | Label | extra args              → agentId = first field, iff it matches a CodingAgents id (case-insensitive)
```
Disambiguation rule: split on `|`; if `parts[0].trim().lowercase()` is a known agent id → 3-field form (`label = parts[1]`, `extraArgs = parts.drop(2).joinToString("|")`); otherwise 2-field form (`label = parts[0]`, `extraArgs = parts.drop(1).joinToString("|")`). Lines with a blank label or fewer than 2 parts are skipped. Trim every field. Joining the remainder with `|` keeps embedded pipes in args.

### Per-task pseudocode with critical details

```kotlin
// Task 2 — CustomVariantParser.kt
package com.forret.llmbrains

object CustomVariantParser {
    const val DEFAULT_AGENT_ID = "claude"

    fun parse(text: String, knownAgentIds: Set<String> = CodingAgents.ids): List<AgentVariant> =
        text.lines().mapIndexedNotNull { index, rawLine ->
            val line = rawLine.trim()
            if (line.isEmpty() || line.startsWith("#")) return@mapIndexedNotNull null
            val parts = line.split("|").map { it.trim() }
            if (parts.size < 2) return@mapIndexedNotNull null
            val first = parts[0].lowercase()
            val (agentId, label, extraArgs) = if (first in knownAgentIds && parts.size >= 3) {
                Triple(first, parts[1], parts.drop(2).joinToString("|"))          // last field keeps pipes
            } else {
                Triple(DEFAULT_AGENT_ID, parts[0], parts.drop(1).joinToString("|"))
            }
            if (label.isBlank()) return@mapIndexedNotNull null
            AgentVariant(
                id = "custom-variant:$agentId:$index",
                agentId = agentId,
                label = label,
                extraArgs = extraArgs,
            )
        }
}
```
Note the `parts.size >= 3` guard: a 2-field line whose label happens to equal an agent id (`codex | --foo`) still parses as a Claude variant labelled "codex" — acceptable and documented by the grammar ("agent-id | Label | args" needs three fields).

### Error handling strategy
- Parser never throws: malformed lines are skipped silently (the settings UI label documents the grammar). No dialogs, no notifications — consistent with the custom-agent feature which also silently hides an incomplete config.
- Unknown agent id in 3-field form → falls back to 2-field interpretation (Claude) rather than disappearing, so the user sees *something* and can correct the label.
- `activeVariantsFor` is only called for active agents, so an orphan custom line for a disabled agent is simply not shown.
- `TerminalCommandRunner.run` already swallows API failures; unchanged.
